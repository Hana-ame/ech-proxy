双代理共存与 bypass.txt：把免费直连和 IP 黑洞流量彻底切开

Clash / Mihomo 虽然内置了 ech-opts（见 Mihomo TLS 配置文档），但它的作用对象是「本机到代理服务器（VPS）」的那一跳握手，且 Mihomo 通用模式 仅包含 rule / global / direct，不会对普通浏览器的直连 HTTPS 做本地 CA 终结（MITM）。因此 ech-proxy 与 Clash 并非重复造轮子，而是天然互补：前者用 ECH / SNI 伪装 / TLS Record 分片免费吃掉仅被 SNI 阻断的站点，后者负责兜底 IP 黑洞与强风控站点。

pac.txt 与 bypass.txt 的互补分工

pac.txt 列出「归 ech-proxy 管的白名单」（被 SNI 阻断但 IP 可直连的站点）；bypass.txt 列出「不要让 ech-proxy 碰的名单」（Google / YouTube 等 IP 黑洞、OpenAI / Claude 等强风控 AI 域名，以及证书固定站点）。Claude 全家桶仅需写入 claude.ai、claude.com、anthropic.com、claudeusercontent.com 四条根域即可覆盖全部子域（见 Claude Code 企业网络配置文档）。

为什么存在 bodyReplay（≤1MB 预读）

HTTP 请求体 req.Body 是一次性流。当 auto 模式在 Fragment → SNI → ECH 之间切换重试，或直连失败逃逸到 -fallback 时，若不预先缓存请求体，第二次发出的 POST 登录/表单会变成空包。代码已将预读严格限定在 ContentLength >= 0 && <= 1MB，普通 GET 零开销，超过 1MB 或流式上传直接透传不占内存。

DNS 解析分层：彻底切断 4545810.xyz 的 DoH 引导死循环

此前日志高频刷屏 netdial.go:572: bootstrap DoH primary endpoints (1.1.1.1/1.0.0.1) unreachable for "4545810.xyz"，根因有三层叠加：第一，为了禁用本地 UDP 53 端口，程序连 https://4545810.xyz/doh 前必须先向 1.1.1.1:443 / 1.0.0.1:443 查 4545810.xyz 的 IP；第二，国内网络阻断或延迟超过 800ms 窗口后虽进入 10 分钟冷却期，但冷却期内代码跳过主端点后仍无条件执行第 572 行 log.Printf；第三，解析全失败时不写负缓存，导致并发请求秒级重入刷屏。

最终方案是将 4545810.xyz（DefaultSiteHost）从 DoH 体系中彻底剥离：在 netdial.ResolveIPs、resolveViaBootstrapDoH 和 ech.ResolveHostIPsByMode 三处入口统一拦截，改走「系统 DNS（5 分钟缓存）→ 失败后原子置位一次性标志 defaultSiteUseBuiltinCF → 进程内永久回退内置 Cloudflare Anycast 广播 IP（104.16.132.229 / 104.16.133.229 及对应 IPv6）」。同时为其余引导 DoH 路径补上了冷却切换单次日志与 15 秒失败负缓存。

解析路径 适用目标域名 核心逻辑与缓存策略
1. IP 字面量直通 纯 IP 目标、-local-ip 指定的 DoH IP 跳过一切 DNS 查询，仅按 -4/-6/-dual 过滤
2. 自有域名专用解析 仅限 4545810.xyz（DoH / PAC / 规则源） net.DefaultResolver 系统 DNS（5m 缓存）→ 失败置位一次性标志，回退内置 CF 广播 IP，绝不走 DoH
3. 业务 DoH 三级解析 普通网站 A/AAAA 及 cloudflare-ech.com type=65 依次尝试 4545810.xyz/doh → 1.1.1.1/dns-query → 223.5.5.5/resolve，按 TTL 缓存
4. 引导 DoH 兜底 业务 DoH 全败时的其他非自有域名（如镜像/第三方 URL） 800ms 优先 1.1.1.1/1.0.0.1 → 切入 10m 冷却（仅打一次日志）串行兜底国内 DoH；全败写 15s 负缓存
5. 上游代理远端解析 命中 bypass.txt 或逃逸至 -fallback 的请求 直接携带原始域名交由上游代理（如 Clash）远端解析

2026 年 TLS 握手对抗边界：为何分片与 ECH 依然有效，却过不了 IP 黑洞

抗审查手段能否奏效，取决于阻断发生在网络协议栈的哪一层。根据 IEEE S&P 2025《Transport Layer Obscurity》、GFW Report《A Wall Behind A Wall》 以及 ACM CCS 2026《CircumVolve》 的实测结果，2026 年的对抗呈现出清晰的四层分化：纯 TCP 分片在部分运营商已失效；TLS Record 分片加 TCP 分片组合对国家出口 GFW 大部分仍有效（90% 以上服务端兼容），但在河南等省级防火墙下会被直接阻断；Cloudflare ECH 依靠加密内层 SNI 与高误伤成本的公共外壳 cloudflare-ech.com 保持高可用（net4people/bbs #584）；而 IP 黑洞在 TCP SYN 阶段即丢包，任何 TLS 层手段都无能为力。

晚高峰连接调优：Happy Eyeballs、多路 HTTP/2 与仅限 ECH 的 HTTP/3 备选

晚高峰（20:00–23:30）国内公网出口丢包飙升时，单 IP 串行拨号与单一 HTTP/2 TCP 连接的队头阻塞会把整页加载拖成幻灯片。在不触碰 Cloudflare 优选 IP（遵守 ToS）的前提下，本轮从三层解决了拥塞放大问题。

  • Happy Eyeballs 并发竞速与故障 IP 冷却：DialContextHappyEyeballs 按健康度重排候选 IP，最多并发 3 路（100ms 阶梯发起），首个 TCP 握手成功立即胜出并关闭迟到连接；超时或握手失败的 IP 自动记入 3 分钟冷却表，避免后续请求死磕同一拥塞节点。
  • 多路 HTTP/2 连接池（4 分片 / 2 分片）：Go 的单个 http2.Transport 对同一 host:443 只会复用 1 条 TCP 连接。将 ECH 拆成 4 个独立 http2.Transport 轮询、SNI/分片拆成 2 个分片，可在不稀释连接复用、不触发多 CDN 子域名连接爆炸的前提下，将单 TCP 丢包的队头阻塞面压缩到 1/4。
  • 仅限 ECH 的 HTTP/3 备选（托盘热开关，默认关闭）：由于裸 QUIC Initial 已遭 SNI 审查且部分运营商限速 UDP/443，HTTP/3 严格仅作 ECH 通道的 H2 失败回退（SNI/Fragment 绝不使用），复用 quic-go v0.59.0 与 Go 1.26 原生 EncryptedClientHelloConfigList，并特意不设 KeepAlivePeriod 以防 quic-go 0-RTT 驱逐 UDP 端口泄漏。

同类开源代理源码实证：性能差距不在加解密，而在连接池与试错链路

对照 ech-proxy、Watt Toolkit（SteamTools） + dotnet/yarp 以及 dev-sidecar 源码核验后可以确认：直连工具的满速带宽上限取决于本地宽带到目标 CDN 的物理链路，真正的架构差异体现在入站/出站协议栈、连接池复用以及冷启动试错成本。

自托管成本边界与 2026 代理生态：为何智利家宽模式在 CN 无法复制

公开 Invidious 实例 nadeko.net（由智利独立开发者 Fijxu 单人维护）每天仅视频中转就消耗超过 7TB（月超 210TB），但全部 30 多项服务的月成本仅约 $123 USD，完全靠加密货币与 Liberapay / BuyMeACoffee 捐赠覆盖。其低成本的核心前提是：智利家宽标配 1Gbps 上下行对称无限流量光纤（如 Tu Mundo）、住宅 IP 天然绕过 YouTube 对机房 IP 的风控（LowEndTalk），且无 80/443 封禁与反 PCDN 严打。在 CN 环境下，家宽上行不对称、反 PCDN 监控、CGNAT/端口封禁与合规红线决定了只能依赖海外节点。
