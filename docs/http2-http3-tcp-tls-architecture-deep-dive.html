HTTP/2 与 HTTP/3 底层协议、代码实现及 TCP/TLS 握手交互架构

从 RFC 标准、帧结构与流控状态机出发，拆解 TCP、TLS 1.3（含 ECH / ALPN）与 HTTP/2、QUIC/HTTP/3 之间的耦合关系，并直接映射到 Go x/net/http2、quic-go/http3 以及 .NET YARP 的真实连接池与代理网关实现。

1-RTT vs 2–3
QUIC 将 TLS 1.3 握手直接嵌入传输层 Initial/Handshake 包，彻底合并了 TCP 与 TLS 的往返延迟，并在丢包时消除跨流队头阻塞。

TCP + TLS 1.3 + HTTP/2 与 QUIC + HTTP/3 的握手交互差异

HTTP/2（RFC 9113）本身依然是跑在 TCP 与 TLS 之上的应用层协议，因此一次冷启动 HTTPS 请求必须严格串行完成三个阶段：TCP 三次握手（1 RTT）→ TLS 1.3 握手并通过 ALPN 协商 h2（1 RTT）→ 发送 HTTP/2 Preface / SETTINGS 与首个 HEADERS 帧。如果目标 IP 被路由黑洞，连接在第一步 TCP SYN 就会超时；如果明文 SNI 被 DPI 匹配，连接会在第二步 TLS ClientHello 后收到伪造 RST。

HTTP/3（RFC 9114）构建在基于 UDP 的 QUIC（RFC 9000）之上，并由 RFC 9001 规定直接复用 TLS 1.3 的握手消息（去掉了 TLS Record 层，改由 QUIC 的 CRYPTO 帧承载）。客户端首个 UDP Initial 包里同时携带了 QUIC 传输参数与 TLS 1.3 ClientHello（含 ALPN h3），服务端回复 Initial + Handshake + 1-RTT 后，客户端在 1 RTT 结束即可发出 HTTP/3 请求帧（复用会话票据时甚至可达 0-RTT）。

HTTP/2 底层原理与 Go x/net/http2 代码实现细节

HTTP/2 将文本协议彻底改为二进制分帧层（Binary Framing Layer）。所有通信被切分为带 9 字节定长头（Length 24b + Type 8b + Flags 8b + R 1b + Stream ID 31b）的帧（HEADERS、DATA、SETTINGS、WINDOW_UPDATE、PING、RST_STREAM、GOAWAY）。客户端发起的流恒为奇数 ID（1, 3, 5...），允许在同一条 TCP 连接上交错收发几十上百个请求，彻底消除了 HTTP/1.1 的应用层队头阻塞。

HPACK 头部压缩

RFC 7541 定义了静态表 + 动态表 + 霍夫曼编码。由于动态表严格依赖 TCP 的全局有序到达，两个流共享同一张动态表状态；这也是 HTTP/2 无法直接搬到无序 UDP 的原因之一。

双层流量控制

HTTP/2 在 TCP 滑动窗口之上又建了连接级 + 流级两套信用窗口（默认 65,535 字节），接收方通过 WINDOW_UPDATE 补充额度。若某条大文件下载流耗尽连接级窗口，其它小请求流也会被卡住。

Go http2.Transport 源码约束

Go 的 x/net/http2.Transport 内部 clientConnPool 以 addr（即 host:443）为 Key。只要当前 ClientConn 未达到对端通告的 MAX_CONCURRENT_STREAMS（通常 100），所有发往同一域名的请求只会复用 1 条 TCP 连接。

在晚高峰国际公网丢包率达到 15%–30% 时，这种“单 TCP 复用 100 条流”的设计会暴露出最致命的短板——TCP 队头阻塞（TCP Head-of-Line Blocking）：内核 TCP 协议栈必须按字节序号严格有序地把数据交给 TLS 与 HTTP/2 解析器。只要单个 TCP 段丢失，哪怕 Stream 3 和 Stream 5 的帧已经抵达网卡缓冲区，内核也必须死等 Stream 1 的那个丢包完成 RTO/快速重传，整条连接上的几十张并发图片全部冻结。

// echproxy/ech/client.go — 用 4 路独立 http2.Transport 分片绕过 Go 单 TCP 限制

    rr   atomic.Uint64  // 无锁轮询，将同一 host:443 的并发流打散到 4 条独立 TCP

HTTP/3 与 QUIC 底层机制：如何用用户态 UDP 消灭队头阻塞

QUIC 把传输层的可靠性、拥塞控制与多路复用全部从操作系统内核搬进了用户态 UDP。每个 QUIC 包由外层包头（含 Connection ID，网络从 Wi-Fi 切到 5G 改了客户端 IP 也能无缝迁移不断连）和加密负载构成，负载内包含多个独立的 STREAM 帧。每个 Stream 拥有独立的字节偏移量与接收重组缓冲区——Stream 1 丢包重传时，Stream 3 和 Stream 5 的数据可以立刻交付给上层 HTTP/3 解析器。

为了适配跨流无序到达，HTTP/3 抛弃了 HPACK，改用 RFC 9204 QPACK：它通过两条专用的单向控制流（Encoder Stream / Decoder Stream）异步同步动态表，并允许请求帧直接引用静态表或已确认的动态表条目，避免头部解码互相阻塞。

协议维度 HTTP/1.1 (RFC 9112) HTTP/2 (RFC 9113) HTTP/3 (RFC 9114 + RFC 9000)
传输层 TCP（内核态） TCP（内核态） QUIC over UDP（用户态）
加密层整合 外挂 TLS Record 外挂 TLS 1.2/1.3（ALPN h2） 内嵌 TLS 1.3 CRYPTO 帧（ALPN h3）
头部压缩 无明文压缩 HPACK（依赖全局有序） QPACK（专用单向控制流，抗乱序）
队头阻塞 应用层 + TCP 层均有 仅 TCP 层仍有 应用层与传输层均消除
连接迁移 不支持（绑定四元组） 不支持（绑定四元组） 支持（基于 Connection ID）

TLS 1.3、ECH、ALPN 与传输层的深层耦合陷阱

TLS Record 层与 TCP 分段的微妙关系

TLS 握手消息（如 ClientHello）运行在 TLS Record 层之上，每条 Record 带 5 字节头（类型 + 版本 + 长度）。一个 ClientHello 既可以在 TCP 层拆成多个 Segment，也可以在应用层主动拆进多个小 TLS Record。正如 IEEE S&P 2025 论文 所证，许多 DPI 仅能重组 TCP 流但未实现跨 TLS Record 的 SNI 拼接，因此应用层 Record 分片比纯 TCP 分片更持久。

ECH（RFC 9460）如何在 H2 与 H3 中复用

ECH 将握手拆成「外层明文 ClientHelloOuter（SNI 填公共壳如 cloudflare-ech.com）」和「内层加密 ClientHelloInner（含真实域名）」。因为 QUIC 直接复用 TLS 1.3 握手消息，Go 1.26 标准库的 tls.Config.EncryptedClientHelloConfigList 既可用于 TCP，也可直接传入 quic-go 的 http3.Transport，使 QUIC Initial 包内的真实 SNI 同样不可见——而不带 ECH 的裸 QUIC Initial 自 2024 年起已被大规模解密审查（ACM CCS 2026）。

ALPN 协商失败与降级路径

服务端不支持 h2 时，echproxy/ech/sni.go 会根据协商结果回退至 HTTP/1.1 池；而 echproxy/ech/h3.go 必须显式设置 NextProtos: []string{http3.NextProtoH3} 并把证书核对挂在 tls.Config.VerifyConnection 回调中，确保在握手完成前即执行 validateUpstreamCert。

quic-go 自定义 Dial 的 UDP 端口泄漏陷阱

在 quic-go v0.59.0 中，http3.Transport.Dial 返回 *quic.Conn，若回调里调用 quic.DialAddrEarly，每次拨号会独占一个系统 UDP socket。如 AdguardTeam/dnsproxy #511 披露，若再开启 KeepAlivePeriod，被驱逐的旧连接会因不断发 PING 而永不空闲超时导致端口耗尽。因此 ech-proxy 的 H3 实现严禁设置 KeepAlivePeriod，并配合 MaxIdleTimeout: 30s 与关闭时主动 tr.Close()。

代理网关代码架构对照：Go（ech-proxy）vs .NET（YARP / SteamTools）

在反向代理/本地 MITM 网关中，入站（浏览器 ↔ 代理）与出站（代理 ↔ 源站）是两套完全解耦的传输状态机。入站可以跑 HTTP/1.1 或 HTTP/2，出站完全可以独立升级为多路 HTTP/2 或 HTTP/3 + ECH；同时，一个网页包含的多个 CDN 子域名（如主站 + 图床 + 静态资源）在代理侧会按 host:443 乘以分片数建立独立连接池，因此分片数必须克制（4 路 ECH / 2 路 SNI 是延迟、内存与风控的平衡点）。

完整发包顺序与响应流生命周期：从 L2 帧到流状态机收敛

无论 HTTP/2 还是 HTTP/3，一次请求都不是“发一个包等一个包”，而是严格按协议层封装与状态机推进的多帧序列。理解逐包顺序能直接解释代理层里的窗口耗尽卡死、RST_STREAM 级联中止与 0-RTT 驱逐等疑难现象。

HTTP/2 发包顺序与响应流（TCP + TLS 1.3）

  • 1. L2/L3/L4 建连：IEEE 802.3 以太网帧（MTU 1500B）承载 IP + TCP SYN（协商 MSS=1460B、WScale、SACK）↔ SYN-ACK → ACK。
  • 2. TLS 1.3 握手：客户端发 0x16 Record 承载 ClientHello（带 SNI/ECH、ALPN: h2；分片模式拆为多个小 0x16 Record）↔ 服务端回 ServerHello + Certificate + Finished。
  • 3. H2 连接序言与请求流：客户端先发 24 字节魔法序言 PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n + SETTINGS（Stream 0）+ 可选连接级 WINDOW_UPDATE；随后在奇数流（Stream 1）发 HEADERS（HPACK 压缩，无 body 时置 END_STREAM=0x1）与 DATA 帧，流状态由 idle → open → half-closed (local)。
  • 4. 响应流交付：服务端回 SETTINGS / SETTINGS ACK → 在 Stream 1 回 HEADERS（:status: 200）→ 连续发多个 DATA 帧（单帧 ≤ MAX_FRAME_SIZE 默认 16,384B），末帧置 END_STREAM 进入 closed；客户端消费响应体时持续回发 WINDOW_UPDATE（流级 + Stream 0 连接级）补充信用窗口。

HTTP/3 发包顺序与响应流（QUIC + UDP）

  • 1. QUIC Initial + 内嵌 TLS 1.3：客户端发 UDP 载荷 ≥ 1200 字节（RFC 9000 防放大攻击强制填充）的 Initial 包，内含 CRYPTO 帧（TLS 1.3 ClientHello + ALPN: h3 + ECH）。
  • 2. 服务端合并回包：服务端在 1 个 RTT 内合并回复 Initial + Handshake（含证书）+ 1-RTT 包。
  • 3. 并行开启控制流与请求流：客户端完成 Handshake 后，在 1-RTT 包内同时打开：单向控制流（Stream ID 2，类型字节 0x00）发 SETTINGS（0x04）；单向 QPACK 编码流（ID 6，0x02）与解码流（ID 10，0x03）；双向请求流（ID 0, 4, 8...，低 2 bit 为 00）发 HEADERS（0x01）+ DATA（0x00）并置 QUIC FIN。
  • 4. 独立响应流：服务端在同一双向 Stream ID 上回传 HEADERS（0x01）+ DATA（0x00）+ FIN。单个 UDP 包丢失仅影响该包所载的特定流，其余双向流与 QPACK 静态表请求毫秒级正常交付。

原始 Bit 级报文格式：从 IEEE 802.3 到 HTTP/2 与 QUIC/HTTP/3

协议性能与 DPI 审查特征全部藏在每一层报文头的原始 bit 布局中：TCP 头的 4-bit Data Offset 决定了 Options（如 Timestamp）能否改变头长（S&P 2025 曾披露省墙仅匹配 20B 固定头长）；TLS 头的 16-bit Length 允许将单条 ClientHello 切进多个合法 Record；QUIC 头的 Fixed Bit、DCID 与 2-bit 前缀变长整数（VarInt） 则构成了无状态路由与 Header Protection 的基础。

IEEE 与 IETF 核心标准规定及对代理设计的硬约束

上层代理的每一个参数（从 MAX_FRAME_SIZE 到 QUIC Initial 1200B 下限、再到晚高峰丢包策略）都不是拍脑袋定的，而是由 IEEE 物理/链路层标准与 IETF 传输/应用层 RFC 逐层传导下来的硬性规定。

标准编号 所属层 / 组织 关键硬性规定 对 HTTP/2 · HTTP/3 代理的实际影响
IEEE 802.3 / 802.1Q L2 以太网 / VLAN（IEEE） 标准以太网载荷 MTU 1500B（802.1Q VLAN Tag 占 4B，PPPoE 再占 8B → 1492B） 直接限定 IPv4 TCP MSS ≤ 1460B（PPPoE 为 1452B）；QUIC 必须做 PMTUD 且避免 IP 分片
IEEE 802.11 L2 Wi-Fi 无线局域网（IEEE） 空口半双工竞争（CSMA/CA）与链路层 ARQ 重传易引入微突发抖动与乱序 无线丢包放大 TCP 队头阻塞，促使多路 H2 分片或 QUIC 连接迁移（Connection ID）收益更明显
RFC 9293 L4 TCP（IETF） Data Offset 单位为 32-bit word（最小值 5 = 20B）；严格按字节序号有序交付 字节流强有序是 HTTP/2 跨流队头阻塞的根源；Options 扩充头长会影响假定 20B 头的中间盒解析
RFC 8446 / RFC 9460 TLS 1.3 & SVCB/ECH（IETF） 单条 TLS Record 明文上限 16,384B；ECH 公钥通过 DNS type=65（HTTPS/SVCB）下发 支持合法的客户端 TLS Record 分片；ECH 强依赖支持 type=65 的 DoH 解析链路
RFC 9113 / RFC 7541 HTTP/2 & HPACK（IETF） 9B 帧头、默认 MAX_FRAME_SIZE=16KB、默认流控窗口 65,535B、HPACK 全局有序 Go 单 http2.Transport 仅开 1 条 TCP，需多 shard 池 + ReadIdleTimeout/PingTimeout 防僵死
RFC 9000 / 9001 / 9114 QUIC & HTTP/3（IETF） Initial 包强制 ≥ 1200B、2-bit VarInt 编码、Stream ID 低 2 bit 标识方向与发起方 1-RTT 建连 + 零跨流阻塞；但自定义 DialAddrEarly 需严控空闲超时防止 UDP socket 泄漏
